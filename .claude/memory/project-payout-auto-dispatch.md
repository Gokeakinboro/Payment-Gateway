**LIVE 2026-07-08 (PR #93).** Fixed Goke's design complaint: "SA cannot release all payouts." Payouts now **auto-disburse** once the merchant wallet is funded and a rail is chosen (the route rail is resolved at batch creation) — **no manual SA release** for the normal case.

**Behavior:**
- **No `scheduled_at` → fire IMMEDIATELY** (async, right after the create response). **`scheduled_at` in the future → fires when due.**
- **SA `/route` endpoint kept ONLY for the exception queue** + per-batch rail override. A dispatch that can't complete (rail LIVE-but-down / insufficient float / cap) leaves the batch in `needs_routing` for SA/merchant to handle.

**Implementation (`routes/payouts.js` + `jobs.js`):**
- Extracted the `/route` disburse logic into **`dispatchBatch({batchId, overrideRailId, actorId, ip})`** — the SAME money code (DB tx debits rail float + inserts rail_disbursements; post-tx calls `palmpay.sendPayout`; on hard-fail refunds float + merchant wallet). Byte-identical; guards became `throw {_client}` instead of `fail(res)`. `/route` is now a thin wrapper (SA). Exported `dispatchBatch` + `autoDispatchDuePayouts`.
- Batch creation: if not future-scheduled, calls `dispatchBatch` immediately (fire-and-forget post-response; `_client` stops just leave it needs_routing).
- Worker **`autoDispatchDuePayouts()`** in `jobs.js` (worker-0, every 30s, env `PAYOUT_DISPATCH_MS`): fires every `needs_routing` batch with `scheduled_at <= now` — delivers scheduled payouts + backstops any immediate fire that didn't land.

**Reminder — payout model is PREPAID:** wallet is debited (amount+fee+VAT) at batch **creation**, not at disbursement (ledger DEBIT/FEE/VAT rows, ref=batch_ref). Firing sends the already-held funds; success = no change to wallet, hard-fail = refund. So a fired payout doesn't reduce the balance *again* (verified w/ Bucksnostar ₦100: 3,000→2,878.50 at creation). Deployed backend-only to 176 (`paylode-core`), no schema change.
